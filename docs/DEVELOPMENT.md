# Development workflow

## Toolchain

- Stable Rust toolchain.
- Windows 10/11 x64 desktop for full runtime verification.
- Node.js 22+ for package validation (`node tests/validate-package.js`) and, if needed, recovery of an earlier Node-based installation.
- WiX v5 (`wix` .NET global tool plus the `WixToolset.UI.wixext` and `WixToolset.Util.wixext` extensions) to build the per-user MSI.

## Validate

From the repository root:

    cargo test --manifest-path server/Cargo.toml --locked
    cargo build --release --manifest-path server/Cargo.toml --target x86_64-pc-windows-msvc --locked
    node tests/validate-package.js

For the resulting Windows binary, these commands do not apply working-set caps:

    server\target\x86_64-pc-windows-msvc\release\memory-sentry-server.exe --version
    server\target\x86_64-pc-windows-msvc\release\memory-sentry-server.exe --self-test

The OS check must be run on a Windows 10/11 desktop edition. GitHub-hosted Windows runners are Windows Server, which is intentionally rejected by the product OS check.

## Build the setup program

The scripts/build-package.ps1 script creates dist/stage, copies the compiled executable, plugin and required documentation into it, then builds installer/wix/Product.wxs into a per-user MSI with the WiX v5 toolset. CI validates the package and uploads only the official MSI plus its SHA-256 checksum. Release automation attaches only those two files; GitHub's autogenerated source archive remains available for source inspection.

Do not put built EXEs, Setup programs, ZIP files, Git bundles, local publishing scripts, checksums, secrets or local logs into source commits.

## Swap a server build while testing

To test a new server build without restarting Spotify or the plugin, run:

    powershell -ExecutionPolicy Bypass -File scripts\swap-server.ps1

The script builds the release binary (pass `-SkipBuild` to reuse the last build) and runs `memory-sentry-server.exe --swap <exe>`. The running instance restores its limits and exits, the new build replaces it in `%LOCALAPPDATA%\Programs\MemorySentryForSpicetify`, and the monitor relaunches. The plugin reconnects by itself on its next poll, so Spotify stays open throughout.

The release mode selector in the dashboard controls whether trimming releases memory only down to the current ceiling (`trimToCap`, default) or as much unused memory as possible. The setting is saved through `/api/config`; aggressive mode requests a one-time trim when applying a manual limit or lowering an automatic ceiling.

## Architecture

The server is implemented in Rust; the Custom App is JavaScript served to Spotify.

- app/index.js: Spicetify plugin installed by the official per-user MSI; automatic English/Brazilian Portuguese localization and missing-server help.
- server/src/lib.rs: platform-independent adaptive policy and unit tests.
- server/src/platform/windows.rs: Win32 process/memory/window primitives, process identity checks, Windows version gate and per-user single-instance lock.
- server/src/runtime.rs: adaptive process monitor, recovery store, loopback API, configuration, logs, upgrade and uninstall actions.
- installer/wix/Product.wxs: per-user MSI product definition, install wizard and custom actions.
- [BENCHMARKING.md](BENCHMARKING.md): repeatable RAM and interaction-latency tests.
- [RELEASE_CHECKLIST.md](RELEASE_CHECKLIST.md): release gates.

## Publishing

Use English Conventional Commit messages and review the exact staged diff. The PR must pass JavaScript validation, policy tests, Windows x64 compilation and setup packaging. Do not merge or publish a stable release until a clean Windows 10/11 desktop test confirms audio continuity, restore, upgrade, crash recovery and uninstall behavior.
