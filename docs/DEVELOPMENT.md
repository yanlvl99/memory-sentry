# Development workflow

## Toolchain

- Stable Rust toolchain.
- Windows 10/11 x64 or ARM64 desktop for full runtime verification.
- Node.js 22+ for package validation (`node tests/validate-package.js`) and, if needed, recovery of an earlier Node-based installation.
- WiX v5 (`wix` .NET global tool plus the `WixToolset.UI.wixext` and `WixToolset.Util.wixext` extensions) to build the per-user MSI.

## Validate

From the repository root:

    cargo test --manifest-path server/Cargo.toml --workspace --locked
    cargo build --release --manifest-path server/Cargo.toml --target x86_64-pc-windows-msvc --locked
    node tests/validate-package.js

For the resulting Windows binary, these commands do not apply working-set caps:

    server\target\x86_64-pc-windows-msvc\release\memory-sentry-server.exe --version
    server\target\x86_64-pc-windows-msvc\release\memory-sentry-server.exe --self-test

The OS check must be run on a Windows 10/11 desktop edition. GitHub-hosted Windows runners are Windows Server, which is intentionally rejected by the product OS check.

## Testing layers and what each proves

Every change lands with an assertion at the layer it lives in, and each layer proves only its own thing:

1. **Core policy tests** (`crates/Core`, plus the shared `Runtime` parser tests in the server suite) run on any OS and prove the adaptive math: demand percentiles, starvation signals, state floors and savings/cap unit rules.
2. **Runtime helper tests** prove the server-side pure functions that a corrupted input would reach (settings JSON booleans and numbers, log rotation, local API request-trust helpers). Win32 side effects stay out of these tests for the same reason the OS check exists: CI is Windows Server.
3. **Static package validation** (`node tests/validate-package.js`) proves the shipped source is coherent: built file lists, manifest stack order, installer stage contents, and the pinned user-facing behaviors the dashboard must keep (such as the per-identity limit field and the composition bar). It is a source-level contract, not a runtime test.
4. **CI** combines all three across x64 and ARM64, and additionally proves both installers build. Green CI means the package builds and the policy is correct; it never proves live behavior on Spotify.
5. **Real-machine validation** is manual and stays required before a stable call: playback continuity, cap restore, upgrade and uninstall on a real Windows 10/11 desktop (see `RELEASE_CHECKLIST.md`; `BENCHMARKING.md` holds the measurement protocol).

This split is deliberate: behavior automatable without Windows desktop semantics belongs in layers 1-4, and everything that can only be learned from a running Spotify is documented as a manual step instead of faked with mocks of the Win32 surface.

## Build the setup program

The scripts/build-package.ps1 script creates dist/stage, copies the compiled executable, plugin and required documentation into it, then builds installer/wix/Product.wxs into a per-user MSI with the WiX v5 toolset. CI validates the package and uploads only the official MSI plus its SHA-256 checksum. Release automation attaches only those two files; GitHub's autogenerated source archive remains available for source inspection.

Do not put built EXEs, Setup programs, ZIP files, Git bundles, local publishing scripts, checksums, secrets or local logs into source commits.

## Swap a server build while testing

To test a new server build without restarting Spotify or the plugin, run:

    powershell -ExecutionPolicy Bypass -File scripts\swap-server.ps1

The script builds the release binary (pass `-SkipBuild` to reuse the last build) and runs `memory-sentry-server.exe --swap <exe>`. The running instance restores its limits and exits, the new build replaces it in `%LOCALAPPDATA%\Programs\MemorySentryForSpicetify`, and the monitor relaunches. The plugin reconnects by itself on its next poll, so Spotify stays open throughout.

The release mode selector in the dashboard controls whether trimming releases memory only down to the current ceiling (`trimToCap`, default) or as much unused memory as possible. The setting is saved through `/api/config`; aggressive mode requests a one-time trim when applying a manual limit or lowering an adaptive ceiling.

## Architecture

The server is implemented in Rust; the Custom App is JavaScript served to Spotify.

- app/index.js: Spicetify plugin installed by the official per-user MSI; automatic English/Brazilian Portuguese localization and missing-server help.
- server/crates/Core/src/lib.rs: platform-independent adaptive policy and unit tests.
- server/crates/Windows/src/lib.rs: Win32 process/memory/window primitives, process identity checks, Windows version gate and per-user single-instance lock.
- server/crates/Spotify/src/lib.rs: the Spotify app profile (executable name, Chromium role classification and command-line sub-labels) behind the generic AppProfile seam.
- server/src/Runtime.rs plus server/src/Runtime/Setup.rs, Store.rs, Api.rs and Monitor.rs: the server binary's in-crate modules for setup and CLI actions, persistence and the event log, the loopback API, and the adaptive monitor.
- server/src/main.rs: the binary entry point that dispatches the configure, monitor, launch, swap and uninstall commands.
- installer/wix/Product.wxs: per-user MSI product definition, install wizard and custom actions.
- [BENCHMARKING.md](BENCHMARKING.md): repeatable RAM and interaction-latency tests.
- [RELEASE_CHECKLIST.md](RELEASE_CHECKLIST.md): release gates.
- [MARKETPLACE.md](MARKETPLACE.md): Marketplace listing and the distribution model.

## Branching and release model

The repository uses two long-lived branches:

- `main` is the stable branch. It holds only released code and carries the release tags (`v*`). It is protected: changes arrive through a pull request with green status checks, and direct pushes, force-pushes and deletions are disallowed.
- `develop` is the integration branch. Every feature, fix and documentation pull request targets `develop`, where CI (JavaScript validation, Rust policy tests and the Windows x64/ARM64 setup build) runs before merge. `develop` is protected the same way.

Do not merge directly into `main`. A release is cut by promoting `develop` into `main` through a dedicated release pull request, then creating the version tag on the resulting `main` merge commit; the publish workflow builds and attaches the per-user MSIs from that tag.

## Publishing

Feature and fix pull requests target `develop`; only the release promotion merges `develop` into `main` (see the branching model above). Use English Conventional Commit messages and review the exact staged diff. The PR must pass JavaScript validation, policy tests, Windows x64 and ARM64 compilation and setup packaging. Do not merge or publish a stable release until a clean Windows 10/11 desktop test confirms audio continuity, restore, upgrade, crash recovery and uninstall behavior.
